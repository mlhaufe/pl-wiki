> Status: **implemented (phases 1–6) on the `nuxt-content` branch** — scaffold,
> modules, data conversion, UI, SEO artifacts and cutover are complete; the
> pages in `content/languages/` are now the single source of truth. Remaining:
> merge PR, flip GitHub Pages source to "GitHub Actions", then post-v1 phases

## 2. Target state

- **Nuxt 4** (app-first structure: `app/app.vue`, `app/pages/…`; requires Node ≥ 22 → we have v26.7.0 ✓)
- **Nuxt UI v4** (`@nuxt/ui` — includes Tailwind CSS v4, `@nuxt/icon`, `@nuxt/fonts`, `@nuxtjs/color-mode` automatically; do **not** add those to `modules`)
- **Nuxt Content v3** (`@nuxt/content` — SQLite-backed collections, Zod schemas, `queryCollection`, MDC, Shiki)
- **SEO modules** — `@nuxtjs/sitemap` (replaces hand-rolled `sitemap.xml`), `@nuxtjs/robots` (replaces the static `robots.txt`), `nuxt-module-feed` (replaces `jekyll-feed`'s `/feed.xml`; RSS 2.0/Atom/JSON, works with SSG). All three are static-generation friendly.
- **Nuxt Studio** (`nuxt-studio`, dev module — free, open-source, self-hostable): visual/Notion-like editor + Monaco, file & media management, and **frontmatter forms auto-generated from the collection schema** (the schema-driven enforcement of our fixed template). Works locally in dev mode out of the box; *production* editing (edit-on-live-site + commit-from-browser) requires SSR server routes for auth — see constraint in §4 costs.
- Static prerender (`nuxt generate`) deployed to the same GitHub Pages URL — no runtime server needed.

## 4. Data architecture (final): one page per language, schema-locked

> Decision: one Markdown page per language under `content/languages/<slug>.md` in a
> `type: 'page'` collection. Accepted conditionally by the owner on two requirements,
> both met below: **(1)** the page template is restricted, and **(2)** the data is
> queryable like a database to power visualizations and faceted search.

### The frontmatter contract (fixed shape)

Every file follows the same frontmatter shape — the same fixed field set as
`_data/languages.yml`, never extended per page:

```mdc
---
title: AgentScript          # native field (SEO/meta) — set by conversion, mirrors name
name: AgentScript
homepage: https://agentscript.org/   # optional
urls: []                    # optional (string[])
logo: /logos/agentscript.png         # optional, normalized to public/logos/*
author: Owen Densmore       # optional
paradigms: [agent-based]    # optional (string[])
influences: [NetLogo]       # optional (string[])
influenced: []              # optional (string[])
note: "A minimalist Agent-Based modeling system…"   # optional
---

Body = wiki prose only (seeded from `note` at conversion; hand-written later).
```

### Condition 1 — restricting the template

1. **Schema validation at build** — the collection's Zod schema (`name` required, rest
   typed/optional) validates every entry when the dump is generated; a malformed frontmatter
   fails the build. `type: 'page'` layers the built-in `path/title/description/seo/body/
   navigation` fields on top (see Collection Types docs), so we never redefine them.
2. **Single shared page component** — `pages/languages/[slug].vue` + one `LanguagePage`
   component render ALL language pages: infobox (logo/homepage/paradigms/influences/
   influenced/note) above the `<ContentRenderer>` prose. Page authors only supply
   frontmatter + body prose — never layout, styling, or components. (MDC component
   whitelisting can be added later if the body needs guarded extensions.)
3. **Generated corpus** — all 377 files are produced by a conversion script from
   `_data/languages.yml`, so normalization starts uniform, not converged.
4. **Schema-driven editing UI (Nuxt Studio)** — Studio's frontmatter forms are generated
   from the collection schema: editors get typed, constrained inputs (strings, optional
   arrays) instead of free-form YAML, so the fixed template is enforced inside the editor
   itself — the ergonomic companion to rule 1.

```ts
// content.config.ts
import { defineContentConfig, defineCollection } from '@nuxt/content'

export default defineContentConfig({
  collections: {
    languages: defineCollection({
      type: 'page',
      source: {
        include: 'languages/*.md',
        prefix: '/'              // content/languages/x.md -> /languages/x
      },
      schema: z.object({
        name: z.string().min(1),
        homepage: z.string().optional(),
        urls: z.array(z.string()).optional(),
        logo: z.string().optional(),
        author: z.string().optional(),
        paradigms: z.array(z.string()).optional(),
        influences: z.array(z.string()).optional(),
        influenced: z.array(z.string()).optional(),
        note: z.string().optional()
      }),
      indexes: [{ columns: ['name'] }]
    })
  }
})
```

### Condition 2 — query the data like a DB

Content v3 builds a **SQLite table per collection, its columns derived from the Zod
schema** (see Advanced → Database): frontmatter becomes relational, typed data.

- **Typed queries** — `queryCollection('languages')` gives `order`, `where` (`=`, `IN`,
  `LIKE`, `IS NULL`, …), `select(...)`, `limit/skip`, `count()`, server- and client-side.
- **Faceted search** — 377 rows is a tiny dataset: fetch the typed columns once
  (`queryCollection('languages').select('name','paradigms',…)`) and compute facet counts /
  filtered sets client-side (e.g. by paradigm, influence, author). It queries the same
  SQLite-backed dataset — no re-parsing markdown per facet.
- **DB-level array matching** — array fields are stored as JSON text columns; server-side
  containment filtering uses the documented `LIKE` operator, e.g.
  `where('paradigms', 'LIKE', '%"imperative"%').count()` for a per-paradigm aggregate.
- **Full-text search** — `useSearchCollection('languages')` (v3 built-in): FTS5 via SQLite
  WASM, BM25 ranking, snippets, automatic prefix matching — a strict upgrade over today's
  regex-on-name filter, no external search library.
- **Visualizations** — any Vue chart lib consumes the typed query results (languages per
  paradigm, per year of origin if added, influence graphs).
- **Nuxt Studio** — edit forms generated from the collection schema; dev mode available
  from Phase 1; production editing is an optional later phase (requires SSR, see costs).

### Drift controls (build-enforced)

1. **Zod schema** — shape/type violations fail dev/build.
2. **`meta` lint** — unexpected frontmatter keys land in Content's built-in `meta` field
   instead of erroring; a build check flags non-empty/unknown `meta` to keep the shape fixed.
3. **One template component** — no per-page layout or component variance possible.
4. **Slug rule** — one shared `slugify()`: lowercase, `+`→`plus`, `&`→`and`, remaining
   non-alphanumerics → `-` (`C++`→`cpp`, `1C`→`1c`); filename stem = slug; collisions
   reported (and disambiguated) at conversion time.
5. **Cross-link integrity** — `influences`/`influenced` resolve name→slug **against the
   collection itself**; unresolved names flagged at build.
6. **Orphan check** — regex-searchable text (e.g. wiki-style `[[Name]]` links) in bodies is
   lint-checked against known names if we adopt it.

### Costs / accepted trade-offs

- ~377 files instead of one YAML: per-file git isolation (no giant-YAML merge conflicts),
  but batch edits touch many files — mitigated via scripted edits, Nuxt Studio, or an
  optional frontmatter lint/fix script.
- **Single source of truth**: after conversion the pages ARE the data; `_data/languages.yml`
  is deleted at cutover (retrievable from git history if a bulk re-normalization is ever
  needed). No parallel registry/loader is maintained.
- Array containment queries are `LIKE`-over-JSON (documented operators don't include a
  native array-contains); fine at this scale, and client-side faceting is the primary tool.
- **Studio production editing needs SSR** — the publish-from-production flow (OAuth at
  `/_studio`, commit-from-browser → CI redeploy) requires server routes (`nuxt build` on an
  SSR-capable platform) and is therefore **not available on GitHub Pages static hosting**.
  We ship dev-mode Studio (registers the module conditionally in dev only, keeping the
  static bundle clean) + the normal git workflow; enabling production editing later means
  adding an SSR deploy target (NuxtHub, Cloudflare, Vercel, …) alongside-or-instead-of Pages.

## 5. UI notes

- Start from a minimal scaffold, not a big template; the docs template (`npm create nuxt@latest -- -t ui/docs`) is a good reference repo if we want `ContentNavigation` etc. later.
- `LangTable`: columns *Logo / Name / Urls*; rows come from `queryCollection('languages').select(...).order('name').all()`; `UInput v-model` filters that array client-side (380 rows — no perf concern); keep sticky header + zebra striping via utility classes. Rows link to `/languages/<slug>` pages.
- `pages/languages/[slug].vue`: wiki page — the page's own frontmatter row rendered as an infobox (logo, homepage, paradigms, influences/influenced cross-links, note) via the single shared `LanguagePage` component; `<ContentRenderer>` for the prose body.
- **Faceted search / visualizations (post-v1)**: facet sidebar (paradigms, influences, author) + chart views computed from one typed `select()` of the collection; text search via `useSearchCollection('languages')` (FTS5).
- Keep external links `target="_blank" rel="noopener"`.
